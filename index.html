Shared AI-assisted development

One AI setup.
Shared by the team.

The same agents, context and tools. Minimal setup for every developer.

work smarter, not harder
Less prompt archaeology. More useful work.

We are not trying to give everyone another tool to configure and babysit. The goal is one shared AI-assisted development setup that every developer can use with minimal local work.

This is how we moved from individual experiments to shared agents, context, integrations and controls.

Version 0.1: copy, paste, hope.

Our first agent was intentionally simple. We told it what kind of work to do, copied a PBI from Azure DevOps, and let it make the requested changes.

That proved the basic idea. The next question was what the agent needed to become reliable and reusable across the whole team.

Lesson 01 · Context

The prompt is only part of the task.

ACCEPTANCE CRITERIA

What must be true when the work is finished?

DISCUSSION

Which decisions and clarifications were added later?

RELATIONS

Which parent, child and related PBIs shape the scope?

PR CONTEXT

Is related work already open or implemented elsewhere?

The PBI had lore. The prompt had a paragraph.

Copying the description was not enough. The agent also needs acceptance criteria, discussion history, parent and child items, related PBIs and sometimes already-open PRs.

Manually collecting that context for every chat is slow and unreliable. The agent needed a direct, controlled way to read it.

  • Read, create and edit work items, discussions and relations
  • Create and inspect pull requests, diffs, comments and linked work
  • Search repositories, branches, commits, files and code
  • Inspect delivery through builds, test runs and pipelines
  • Access more Azure DevOps services through the same MCP connection
What changed Agents read external context quickly while permissions keep writes controlled. No more context relay race.

We connect Azure DevOps through Microsoft’s MCP server. The agent can fetch work items, relations, discussions, repositories and PR information with the user’s existing access.

The Azure DevOps MCP server supports both reading and writing across work items, repositories, pull requests and delivery services. Existing Azure DevOps permissions and the agent's approval rules still control which actions are allowed.

The team problem

How does the setup work for everyone?

Improves an agent or adds a missing rule.

Manual sharing

Files move through chat, wiki pages or copied settings.

Developer B

Has an older version with different behavior.

New colleague

Nothing scales like “I’ll send you my settings.”

A good personal setup still leaves a distribution problem. Copying agent files and settings manually creates drift, and onboarding depends on who remembers the latest steps.

We needed the setup to be versioned, reviewable and easy to update for the whole team.

Lesson 03 · Conventions

The codebase has rules the agent cannot see.

In our heads

We know the layers, naming, security boundaries, validation style and which existing pattern to copy.

We also know which “technically valid” solution would be wrong for this team.

In the model

The same task can be solved ten plausible ways unless we provide the local constraints.

Without guidance, every session can make a different architectural choice.

Ten implementations enter. One convention leaves.

Developers carry a large amount of codebase knowledge in their heads. The model sees source files, but it does not automatically know which architecture, naming and safety constraints the team considers correct.

AI can produce many valid-looking implementations. We need it to choose the one that fits our codebase.

Instructions · Rules as context

Write down what “good” means here.

ALL

Shared rules

Never invent business rules. Keep scope minimal. Preserve user changes. Report a check only when it ran.

.NET

Backend rules

Dependencies point inward. Keep controllers thin. Pass cancellation tokens. Return ProblemDetails.

UI

Frontend rules

Use Baloise components and events. Keep transport in services. Follow established test patterns.

Tribal knowledge, now searchable as Markdown.

We wrote the team’s rules down in three layers. Shared rules apply everywhere; backend and frontend instructions load only for matching files.

The examples on screen are real rules from DevTools. They cover business ambiguity, scope, validation, architecture, security and framework-specific patterns.

Lesson 04 · Responsibility

One agent for everything is good at nothing.

General-purpose agent

One long prompt, every tool, unclear write rights and a different workflow depending on the request.

Broad accessVariable output

Specialized agents

One responsibility, fixed stages, only the tools it needs and an output structure we can review.

Focused toolsExplicit gates
One agent, seventeen hats, zero dress code.

Implementing a PBI, reviewing a PR, maintaining API requests and preparing backlog work are different jobs. They need different tools, permissions and stopping points.

A single general agent made those boundaries unclear. Specialized agents make the workflow predictable.

Fewer hats. Fewer surprises.

The write-enabled Implement PBI agent still stops at a hard approval gate. PR Review remains read-only. Bruno Sync proposes collection updates, and Grey-ops helps the technical lead prepare and create only approved backlog items.

The tools and permissions are part of each agent definition, not an informal promise.

Lesson 05 · Continuity

Research trapped in chat is temporary.

Read

The agent collects PBI context, code patterns and Git state.

Reason

It identifies facts, assumptions, unknowns and blockers.

Plan

It maps acceptance criteria to files, behavior and checks.

Lose?

A closed session should not force the team to repeat that work.

Chat memory is not project memory.

The Implement PBI agent does substantial work before it touches code: requirement analysis, code research, Git checks, questions, risks and an acceptance-criteria plan.

That research should be reviewable and reusable even when the chat is closed or another developer continues the task.

Implement PBI · Artifact

Save the research. Stop at approval.

artifacts/Beheerstool/PBI-419183.md

1Facts and confirmed requirements
2Assumptions, unknowns and blockers
3Relevant code, tests and Git state
4Acceptance criteria mapped to evidence
5Implementation plan and quality gates
Approve implementation?

No code, branch or Azure mutation before the human answers blockers and approves the plan.

The artifact remembers so we do not have to.

The artifact is a local continuity cache at a predictable project and PBI path. It records the evidence, open questions, plan, pre-existing changes and later the validation results.

The agent presents the plan and asks “Approve implementation?” This is a hard gate: no code, branch or Azure mutation before clear human approval.

02Find relevant code, tests and local patterns
03Write facts, questions and AC mapping to the artifact

The dramatic moment where the agent does not code.

During the demo, focus on the quality of the research rather than lines of generated code. The agent should retrieve linked context, locate the implementation surface, expose missing information and write the artifact.

The key proof is that it stops before implementation and asks for approval.

Demo 02 · PR to finding

PR → actionable finding.

pr {PR-ID} Beheerstool
01Combine the complete diff with PBI acceptance criteria
02Trace changed behavior beyond changed lines
03Report severity, evidence, impact and a concrete fix
04Stay read-only: never post, edit or merge
A reviewer with no merge button. On purpose.

Use a small PR with one known defect and a missing test. Show that the review agent fetches linked requirements, reads complete diffs and follows behavior into callers and tests.

It produces evidence-based findings but has no authority to post comments, edit code or merge the PR.

Where it still breaks

What the workflow does not solve.

01 · REQUIREMENTS

PBIs still lack detail

Field rules, permissions, validation and error behavior must be explicit.

02 · SLICES

Work is still too large

Large Features and PRs consume context and create avoidable merge conflicts.

03 · REVIEW

AI is not a guarantee

Small PRs, automated checks and focused human review still matter.

04 · PLANNING

Unknowns arrive too late

Dependencies and business questions need answers before development starts.

AI cannot clarify the PBI retroactively. Yet.

The workflow makes missing context visible, but it cannot invent the answer. PBIs still need concrete business rules, and work still needs to be split into small independent slices.

AI review remains one check among several. The larger improvement is to surface dependencies and questions during planning rather than during implementation.

The final step closes the loop: useful friction becomes an improvement to the shared DevTools setup.
