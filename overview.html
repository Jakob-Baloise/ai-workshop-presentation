The assistant provides capability; the setup gives it purpose and boundaries.

A coding agent is not a separate AI model. It is a coding assistant prepared for a particular type of work.

The job, team context and developer checkpoints make its behavior more repeatable. For example, our implementation agent researches a PBI, proposes a plan and waits for approval before changing product code.

One assistant, different jobs

The same coding assistant can run an implementation agent or a PR review agent. Each receives different instructions, tools and checkpoints for that job.

The developer remains responsible

The agent can research, propose and implement, but it does not supply missing business decisions. The developer approves the plan and reviews the final code.

Why define a workflow?

A repeatable workflow makes expected steps visible and lets the team improve the setup instead of recreating prompts for every task.

A useful test for any agent

Before sharing an agent, the team should be able to answer four questions:

  • What specific job does it perform?
  • Which project and team context does it need?
  • Which tools may it use?
  • Where must a developer review or approve its work?

The shared setup should be a foundation, not a restriction.

A small example

If the frontend build command changes, we update the project quality gates once. The implementation agent then uses the corrected command for every developer working on that project.

What should stay local?

Project-specific behavior belongs with that project or in scoped instructions. Only patterns that are genuinely useful to others should move into the shared foundation.

Ownership question

Question: Who reviews and maintains shared agents and instructions when they are used across multiple teams?

When should an improvement be shared?

  • The same friction appears in more than one task.
  • The change is stable enough for another developer to use.
  • Its scope is clear: shared, team-specific or project-specific.
  • Another team member can review the behavior before distribution.

The agent does the legwork. The developer decides.

Approval happens before product code is changed.

The workflow is not fully automatic. The most important step is the plan review before implementation.

The final review is also shared: the agent provides checks and findings, while the developer remains responsible for accepting and delivering the change.

What the developer types

The developer selects Implement PBI and supplies a work-item ID and project. The agent opens the correct sources and begins its research.

Two clear human points

The developer answers missing business questions and approves the implementation plan. The developer also reviews the final change before commit, push or PR creation.

What we can inspect

The work document records the sources used, assumptions made, files planned, checks required and final results. Git shows the actual code changes.

Where the workflow deliberately pauses

  • After research, when requirements are missing or contradictory.
  • Before implementation, while the developer reviews the proposed plan.
  • After validation, while the developer reviews the diff and test results.

These pauses are part of the workflow, not failures of automation.

Simple example · Why the request matters

A clear PBI means less guessing.

Unclear PBI

“Add an export button.”

The agent must guess what is exported, which format to use, what filters apply and what happens when there is no data.

Clear PBI

Export the filtered invoice list

  • Download a CSV when the user selects Export.
  • Include the currently filtered rows and visible columns.
  • Use the column names shown in the table.
  • Disable Export when there are no matching rows.
The agent can research the code, but it should not invent the business behavior.

This fictional example keeps the point simple. Better requirements let the agent find the relevant code, propose useful tests and create a focused plan.

With the unclear version, the agent should stop and ask questions rather than choose the behavior itself.

What becomes easier

The agent can identify the table state, CSV generation, button state and focused tests without first asking what “export” is supposed to mean.

When the PBI is unclear

The agent should list the missing decisions and stop. The product owner or developer supplies the business answer before implementation continues.

The practical lesson

Agents make unclear requirements visible quickly. They do not remove the need for clear acceptance criteria.

Questions hidden by “Add an export button”

  • Which records and columns are included?
  • Which file format and filename are expected?
  • Do the current filters and sort order apply?
  • What happens when no rows match?
  • Which permissions or data restrictions apply?

The artifact is working memory, not extra project documentation.

The artifact is a short local work document. It keeps the agent’s research and the developer’s decisions outside temporary chat history.

It is updated during the task: first with research and questions, then with the agreed plan, changed files and exact validation results.

How it changes during the task

Research adds facts and questions. Developer answers become decisions. Implementation adds touched files. Validation adds the exact commands and outcomes.

What it is not

It is not the permanent source of business requirements and does not replace the PBI, code review or PR description. Those systems remain authoritative.

When it is useful

Use it for work that needs research, decisions or continuation across sessions. A tiny one-step change does not need a large artifact.

What a useful artifact records

  • Confirmed facts and the sources used.
  • Open questions, assumptions and developer decisions.
  • The agreed implementation plan and expected files.
  • The exact checks that ran and their outcomes.

Durable outcomes still belong in the work item or pull request when they need to be shared beyond the task.

Where we want to end up

Share the basics. Keep room to adapt.

Shared across teams

A supported base setup

Approved connections, setup guides, common engineering rules and reusable starter agents.

Chosen by each team

Team workflows

Project mappings, quality checks and agents for the work that team performs regularly.

Chosen by each developer

Personal helpers

Private agents and instructions that can stay personal or be proposed back when useful.

The resultTeams do not rebuild the basics, but they are not forced into one identical way of working.
Reuse should be easy; sharing should be a choice.

The end goal has three levels. A small supported foundation is shared across teams. Each team adds its own workflows. Developers can still keep personal helpers.

Useful personal or team additions can be reviewed and moved into the shared layer later.

One example at each level

Approved Azure DevOps access is shared. Beheerstool quality gates belong to the team setup. A developer’s experimental refactoring agent can stay personal until the team wants it.

Keep the shared layer small

Only stable, broadly useful setup belongs in the shared foundation. Product rules stay with their product, and experiments remain local until reviewed.

What we want to enable

A new team can start without recreating setup, then adapt it without waiting for a central group to design every workflow.

How to decide the right level

  • Shared: stable setup that is useful across teams.
  • Team: workflows and checks tied to that team's delivery work.
  • Personal: experiments and helpers that have not yet earned wider adoption.

Useful additions can move outward after they are understood and reviewed.

What is currently in the way

The approach works. The setup is still fragmented.

Tool readiness

Claude setup is not mature

Authentication, VPN, MCP setup and IDE integration are not reliable enough for our workflows.

Tool differences

Capabilities are inconsistent

Agents, instructions and connections do not work the same way across Copilot, Claude and different IDEs.

Shared foundation

Teams still start separately

There is no supported cross-team package of agents, instructions, rules and guides to reuse.

Distribution

Setup is still manual

Developers must configure agent locations, instructions and MCP servers themselves.

Security

Approved connections are unclear

We need a clear list of allowed MCP connections and a route to approve new ones.

Internal access

Important systems are disconnected

Tools such as Valumation need a usable API or approved MCP connection.

Some blockers cannot be solved by one development team.

These are practical blockers we experience today. Tools behave differently, installing the shared setup still requires manual configuration, and access to approved or internal systems is unclear.

What developers experience

A workflow can work in one tool but fail in another because authentication, VPN behavior, available models or MCP support differ. Teams then spend time rebuilding setup rather than improving the workflow.

Security question to resolve

We need to know which MCP servers, source systems and data types are approved. A new connection should follow a clear review process instead of an informal team decision.

Support needed

Define the MCP approval route, improve distribution of the base setup and identify who can provide supported access to internal systems such as Valumation.

What the team can and cannot solve alone

  • Team-owned: improve agent workflows, instructions and project mappings.
  • Shared support: simplify installation and distribution across workstations.
  • Organization-owned: approve connections and provide supported access to internal systems.
  • Vendor-dependent: close capability differences between tools and IDEs.
Optional detail · Connected tools

MCP connects the agent to a system. The system still controls access.

In normal language

A defined way to ask a system

The agent uses a named tool to retrieve or update information instead of relying on manual copy and paste.

Technical term · MCP

Model Context Protocol

A standard interface exposes named tools to the AI client. The connected system still controls identity, permissions and available operations.

01 · Connection requested→02 · Security and owner review→03 · Approved configuration→04 · Available to teams
Approve the connection and its operations before making it available to teams.

MCP provides a standard way for the agent to call tools. It does not replace authentication, authorization or owner approval.

The connected system still decides what the developer may access, while the organization decides which connection may be offered to teams.

Current examples

DevTools currently configures Azure DevOps, Playwright browser automation and AG Grid documentation. Access still depends on the developer’s environment and credentials.

What approval should cover

Server ownership, authentication, operations exposed, data handled, logging, maintenance and how access can be withdrawn.

Questions for every proposed connection

  • Who owns and maintains the MCP server?
  • Which operations and data does it expose?
  • How is the developer authenticated and authorized?
  • What is logged, and how can access be removed?
  • Who approves changes to the connection?
Practical lessons so far

What has worked for our team.

01

Start with one task

A clear workflow is easier to improve than a general assistant.

02

Give each agent a clear job

Implementation and review need different behavior and permissions.

03

Plan before changing code

Missing requirements are cheaper to solve before implementation.

04

Keep developer decisions visible

Approval and final review should never be implied.

05

Use normal engineering checks

Generated code still needs tests, linting, builds and review.

06

Improve the shared setup

Fix the reusable workflow instead of teaching the same lesson repeatedly.

The useful knowledge belongs in the workflow, not in personal prompt history.

These are working lessons, not universal rules. They come from building and refining the current agents.

The final lesson is the most important for scaling: repeated friction should result in a shared improvement.

How we improve an agent

When a workflow fails or asks unnecessary questions, we identify whether the cause belongs in the agent, a shared rule, project configuration or documentation, then change the narrowest shared file.

What we avoid

Large agents with every tool, hidden business assumptions, automatic writes without a clear gate and claims that a change passed checks that were not actually run.

What to test next

Whether these lessons remain useful when another team adopts the setup without help from the people who created it.

A useful next experiment

  • Give one other team the base setup and a small number of agents.
  • Observe which setup steps still need direct help.
  • Record which improvements they can reuse and which remain team-specific.
  • Check whether developers understand the approval points without extra explanation.
