A short look back

We started scattered.

Four developers, four different ways of working. AI was just an isolated chat window with no link to the ticket, the code or our rules, so it mostly guessed. And whatever one person figured out stayed with that person.

How it used to work

In the past we used the Visual Studio Copilot chat window to ask questions. Sometimes it had a little context to work with, but most of the time it understood very little about the project. Everyone also worked in their own way, which gave mixed and unpredictable results.

Why that held us back

A chat window only knows what you paste into it. Without the ticket, the code and our standards, it cannot know our naming, our patterns or what "done" means here, so it fills the gaps with guesses. Those guesses then cost time in review and rework.

The bigger problem

Whatever one person figured out stayed with that person. The old way produced useful snippets, but it was personal and unpredictable, so the team could not rely on it or build on it.

The agents we have

Each agent is focused on one job. Today we have, among others:

  • Implement PBI: takes a ticket from research to reviewed code.
  • PR Review: reviews a pull request or a local change for issues.
  • Feature decomposition: breaks an epic into PBIs and tasks.
  • Bruno sync: keeps our API test collections up to date.
  • Explore: fast, read-only questions about the codebase.

How an agent is built

An agent is a file that describes four things: the job it does, the instructions and rules it must follow, the tools it may use, and where a person must approve or review. They all load the same shared rules, so their behaviour stays consistent.

What is an MCP server?

MCP stands for Model Context Protocol. It is a standard way to plug an AI assistant into another system. Instead of copy-pasting information into a chat, the assistant calls a named tool that talks to the system directly. The system stays in charge: the developer signs in with their own account, and the system decides what they may read or change.

Which servers we use today

  • Azure DevOps: read and update work items, discussions, pull requests, branches, commits and pipelines.
  • Playwright: drive a browser to check the running user interface.

Why it is handy

The assistant pulls the real work item, reads the acceptance criteria and checks the actual UI on its own. Far less manual copy-paste, fewer mistakes and much more relevant results.

Our coding standards

The rules are our shared standards for how we build and test: backend, frontend and general conventions. They include the unwritten rules we used to keep in our heads, now written down so the assistants and new joiners follow them too.

Documentation

Alongside the rules, the setup points to our project documentation and references. This is context the assistant reads to follow how we actually do things here. It is reference material, not a live connection.

Everything in one repository

The agents, their instructions, the shared rules and the project configuration all live in one version-controlled repository in Azure DevOps, the same way our code does.

Why that matters

Every change is proposed, reviewed and recorded, so the setup is transparent, reversible and shared. Anyone can pull the latest version and get the same, improved setup.

Two clear human checkpoints: approve the plan, review the result.

The five steps

Understand the work, investigate the facts, decide the plan, build the code, and review the result. The assistant does the legwork; people make the decisions.

The two checkpoints

  • Before any code is written, a developer approves the plan.
  • Before anything is delivered, a developer reviews the result.

Fast, but not wise

The AI is fast at reading, searching and drafting, but it does not understand our business. People decide what is actually right.

A shared work document

As it works, the agent keeps a short work document, the artifact. It records what it found, the questions it asked, the agreed plan, the files it changed and the checks it ran.

Why it helps

It keeps the reasoning and decisions out of throwaway chat history. A developer can review how a conclusion was reached, and another person can pick the work up later.

What it is not

It is working memory, not project documentation. The real requirements stay in the work item and the final outcome stays in the pull request. Durable decisions are copied there once approved.

Plan before building

Agreeing a short plan first makes the assistant's intentions visible while they are still cheap to change. Catching a wrong assumption in the plan takes a minute; catching it after the code is written takes far longer.

The most valuable checkpoint

This is the single most useful moment for a person to step in, because a small correction here saves a lot of rework later.

Analyse and implement

First the agent analyses the epic: it reads the requirement, drafts a PBI breakdown and asks where the scope is unclear. Then, when we ask it to implement one PBI, it gathers the context itself through Azure DevOps and our rules.

Plan, build and review

It proposes a short plan and pauses for approval. After approval it writes the code and its tests and runs the checks. Finally the review flags a possible improvement, we decide whether to apply it, and a developer gives the final approval before a pull request is opened.

Connected to more of our systems

Shared toolkits for every team

A new team could start from a ready-made pack of agents, rules and setup, then adapt it. Concrete examples:

  • A starter pack with the Implement PBI and PR Review agents already configured.
  • Backend and frontend rule sets a team can switch on and tweak.
  • Project templates that resolve the right repository, branch and checks automatically.
  • A short guide so a new joiner is productive on day one.

Connecting more systems

Through reviewed MCP connections, the assistants could reach more of what we use daily. Ideas we could explore:

  • Confluence or SharePoint: read our specs and internal documentation.
  • Jira: for teams that track work there instead of Azure DevOps.
  • Test management: link code changes to test cases and results.
  • Monitoring and logs: help investigate an incident from the real error data.
  • Design tools: read a Figma design when building a screen.

Each new connection is reviewed first, and the system keeps control of access.

More automated checking

More of the routine checking could run on its own, so people focus on judgement:

  • Automatic test suggestions for changed code.
  • A first-pass review on every pull request that flags obvious issues.
  • Checks for accessibility, security and performance basics.
  • Spotting missing edge cases before a human reviews.

More agents over time

As we notice repeatable jobs, we add focused agents and share them. Candidates we have thought about:

  • A test-writing agent for existing untested code.
  • A documentation agent that keeps READMEs and API notes current.
  • A dependency-update agent that proposes and tests upgrades.
  • A release-notes agent that summarises what changed.

Knowing it is worth it

To invest well, we would watch a few simple signals:

  • Time saved per task, especially on context gathering.
  • How consistent the output is across people.
  • How quickly new joiners become productive.
  • Fewer issues found late, in review or after release.

Still new, moving fast

Working with AI changes almost every month. Using it well is a skill that takes practice, and our shared setup is never truly finished.

An ongoing investment

Getting value from AI is an investment, not a one-time switch. The teams that learn it now will be ahead as the tools mature.

Not experimented with yet

Recent capabilities we have not really used ourselves:

  • Background agents: hand a ticket to an agent that works on its own and comes back with a pull request to review.
  • Parallel agents: several agents working on different tickets at the same time.
  • Spec-driven development: write a clear specification and let the agent implement against it.
  • Plain-language interfaces: ask for a change in words, away from the editor.
  • Bulk test generation across a whole area of the codebase at once.
  • Self-updating documentation that follows the code.

Where the field is heading

  • Autonomous coding agents that take a whole issue end to end, such as GitHub's Copilot coding agent, Claude Code, Cursor and Devin.
  • Agents that use a computer like a person, clicking through a browser or app to finish a task.
  • Much larger memory, so an agent can hold a whole project in context at once.
  • Teams of specialised agents that plan, build, test and review together.
  • A growing catalogue of MCP connections to plug into almost any tool.
  • Private, on-device models for sensitive code that cannot leave the company.

Not all of this is ready or right for us yet, but it shows where things are going.

What helps us keep up

Time and support to keep learning and refining, so the investment compounds instead of stalling. A little room to experiment safely is what turns fast-moving tools into real value.
